# Sparse-vLLM 当前推理流程详解

## 1. 总览

Sparse-vLLM 是一个稀疏注意力推理引擎，在 vLLM 风格调度框架上加入 KV cache（Key/Value 缓存，即 Transformer attention 中历史 token 的 K/V 张量缓存；它让 decode 阶段不用重复计算历史 token 的 K/V）稀疏管理。核心组件调用链如下：

```
sparsevllm.LLM (入口)
  → LLMEngine (引擎主循环)
    → Scheduler (调度器，选择 prefill/decode batch)
    → ModelRunner (模型执行器，管理权重、KV cache、前向计算)
      → model(input_ids, positions) (模型前向)
        → Attention.forward() (每一层的 attention 计算)
          → CacheManager (物理 KV 存储管理)
          → SparseController (稀疏策略决策)
```

**vanilla 路径与 attnpredict-offload 路径的共同点：**
- 共享同一个 `LLMEngine.step()` 主循环；
- 共享同一个 `Scheduler` 调度逻辑（prefill 优先，不混跑 prefill/decode）；
- 共享同一个 `Attention.forward()` 通用流程；
- 共享同一个 `SparseController` 框架接口。

**分叉点：**
- `CacheManager.create()` 工厂方法根据 `config.vllm_sparse_method` 创建不同的 cache manager；
- vanilla 使用 `StandardCacheManager`，attnpredict-offload 使用 `AttnPredictOffloadCacheManager`；
- 分叉体现在：KV 物理存储策略、slot 分配方式、decode 视图构建、是否使用 predictor、是否有 CPU/GPU 数据搬运。

## 2. 初始化流程

### 2.1 从 `sparsevllm.LLM` 到引擎就绪

`LLM` 是 `LLMEngine` 的空别名（[llm.py:4](src/sparsevllm/llm.py#L4)）。`LLMEngine.__init__` 完成以下步骤：

1. **Config 创建**：从用户 kwargs 和 `Config` dataclass 字段过滤出有效参数，创建 `Config` 实例。`Config.__post_init__` 会加载 HF 模型配置、验证参数合法性、自动推导 `obs_layer_ids` 等。

2. **TP 子进程启动**：为 rank 1..N-1 各启动一个独立进程运行 `ModelRunner`，通过共享内存做 RPC 通信。

3. **Rank 0 ModelRunner 创建**：
   - 初始化 NCCL 分布式环境；
   - 加载模型权重（Qwen2/Qwen3/DeepSeek-V2/Llama）；
   - 调用 `CacheManager.create()` 创建 cache manager（**关键分叉点**）；
   - 创建 `SparseController`，注入到模型的每一层。

4. **Tokenizer 加载**：`AutoTokenizer.from_pretrained`。

5. **Scheduler 创建**：接收 cache manager 引用，用于查询剩余显存。

6. **Warmup**：运行一次 dummy prefill+decode，触发算子编译和内存分配。

### 2.2 vanilla 的 `StandardCacheManager` 初始化

[standard.py](src/sparsevllm/engine/cache_manager/standard.py)：

- 调用 `_get_available_slots_info()` 计算可用显存，得出 `num_kvcache_slots`；
- 分配单一全局 GPU KV cache 张量：`kv_cache[2, num_layers, num_slots, num_kv_heads, head_dim]`；
- 初始化 `free_slots_stack`（GPU slot 栈）、`buffer_req_to_token_slots`（全局 row/pos→slot 映射表）、`seq_id_to_row`、`row_seq_lens`。

### 2.3 attnpredict-offload 的 `AttnPredictOffloadCacheManager` 初始化

[attnpredict_offload.py](src/sparsevllm/engine/cache_manager/attnpredict_offload.py)：

不调用 `StandardCacheManager.__init__`，只复用基类 `CacheManager` 的模型尺寸/配置初始化。额外初始化：

1. **GPU active pool**：每层独立的可复用 slot 池，形状与 vanilla 相同但语义不同——只保存当前驻留 GPU 的 token KV。每层各有 `free_slots_stack`、`buffer_req_to_token_slots`（GPU 侧）、`gpu_req_to_token_slots_cpu`（CPU 侧镜像）。

2. **CPU full backing**：`cpu_kv_cache[2, num_layers, cpu_num_slots, num_kv_heads, head_dim]` 保存完整历史 KV。CPU slot 是跨层共享的逻辑 token slot。`cpu_req_to_token_slots` 记录 row/pos→cpu_slot 映射。

3. **Predictor 状态**：复用父类 `AttnPredictCacheManager` 的 `_init_attnpredictor_state`——CNN 模型、`attn_history`（滚动 attention 历史）、`tsp_mask`（预测 mask）、`_last_decode_view`。CNN 使用 `torch.compile(dynamic=True, options={"triton.cudagraphs": False})` 编译，并在初始化时做最大宽度 dummy prewarm。

4. **异步预取资源**：
   - 单条默认优先级 `torch.cuda.Stream(priority=0)` 作为 prefetch stream；
   - `ThreadPoolExecutor` 后台线程池；
   - `_prefetch_futures[layer_idx]` 每层后台任务句柄；
   - `_layer_locks[layer_idx]` Python 锁保护 per-layer 元数据。

5. **Lease 和 residency 状态**：
   - `_lease_hot_positions[layer]`：当前复用的 hot positions（row→positions）；
   - `_lease_start_positions[layer]`：lease 起始 decode 位置；
   - `_resident_positions[layer]`：GPU 驻留集合（row→set of positions）；
   - `_dirty_gpu_positions[layer]`：GPU 新写入但未同步到 CPU 的 token；
   - `_static_view_cache[layer]`：lease 内稳定的 sink/hot slots 缓存；
   - `_packed_slots_cache[layer]`、`_packed_positions_cache[layer]`：decode packed view 缓冲复用。

## 4. step 主循环

[llm_engine.py:268](src/sparsevllm/engine/llm_engine.py#L268)：

```
step():
  1. scheduler.schedule() → (seqs, is_prefill, preempted_seqs)
  2. 释放被抢占序列的 KV slots
  3. model_runner.call("run", seqs, is_prefill) → (token_ids, attn_score)
  4. scheduler.postprocess(seqs, token_ids, is_prefill)
  5. 释放已完成序列的 KV slots
  6. 返回 (finished_outputs, num_tokens)
```

**调度器如何区分 prefill 和 decode**：Scheduler 维护 `waiting` 和 `decoding` 两个队列。`schedule()` 先尝试从 `waiting` 取 prefill 序列（prefill 优先），只有 `waiting` 为空时才从 `decoding` 取 decode 序列。单次 step 不混跑。

## 5. prefill 流程

### 5.1 vanilla prefill

`StandardCacheManager._prepare_prefill()`：

1. 为每个序列的当前 chunk 分配 GPU KV slots（从 `free_slots_stack` 栈顶取）；
2. 构造 `input_ids`、`positions`、`slot_mapping`、`cu_seqlens_q`；
3. 更新 `buffer_req_to_token_slots[row, pos] = slot_id`；
4. 设置 `layer_batch_state`（所有层共享同一状态）。

`Attention.forward()` 中：
- `store_kvcache()` 将当前 chunk 的 K/V 写入 GPU cache；
- `context_attention_fwd()` 做完整 prefill attention，读取 `buffer_req_to_token_slots` 中该序列的全部历史 slot。

### 5.2 attnpredict-offload prefill

`AttnPredictOffloadCacheManager._prepare_prefill()`：

1. 为每个序列的当前 chunk 分配 **CPU full backing slots**（`_allocate_cpu_slots`）；
2. 为 **每一层** 分别分配 GPU active slots（`_allocate_gpu_slots_locked`），更新每层的 `gpu_req_to_token_slots_cpu` 和 `buffer_req_to_token_slots`；
3. 设置每层独立的 `LayerBatchStates`（`slot_mapping`、`context_lens`、`req_indices`）。

`Attention.forward()` 中：
- `store_kvcache()` 写入 GPU active pool；
- `on_kv_stored()` 同步写入 CPU full backing（prefill 时立即写，不做 lazy）；
- `prepare_prefill_predictor_inputs()` 在最后一个 prefill chunk 创建 4D `tail_score` 缓冲区 `[batch, num_heads, history_step, ceil(max_len/block_size)]`；
- `context_attention_fwd()` 做完整 prefill attention，同时旁路写 `tail_score`；
- `on_prefill_layer_end()` 提交后台任务：CNN 预测首个 decode 的 hot tokens + 预取。

**为什么 prefill TTFT 比 vanilla 慢**：每层每 chunk 都要额外做 CPU full backing 写入（D2H copy + CPU `index_copy_`），且每层都要为 GPU active pool 分配 slot。Nsight Systems 显示 `cudaMemcpyAsync` 占 CUDA API 时间 98.3%，其中 D2H 占 84.3%。

## 6. decode 流程

### 6.1 decode 共同逻辑

- 每个 step 每个序列只输入最后一个 token（`seq.last_token`）；
- `input_ids = [seq.last_token for seq in seqs]`，`positions = [seq.num_tokens - 1]`；
- attention 用历史 KV 和当前 query 计算输出；
- 生成下一个 token 后 `seq.append_token(token_id)`；
- KV cache 增加一个新 token 的 K/V。

### 6.2 vanilla decode

`StandardCacheManager._prepare_decode()`：

1. 为每个序列分配 1 个新 GPU slot（`_allocate_batch`）；
2. 更新 `buffer_req_to_token_slots[row, cur_len] = new_slot`；
3. 设置 `layer_batch_state`（所有层共享）。

`Attention.forward()` 中：
- `get_layer_store_view()` 直接返回全局 KV cache 和 slot_mapping；
- `store_kvcache()` 写入新 token 的 K/V；
- `get_read_view()` 返回 `buffer_req_to_token_slots`（完整映射表）；
- decode attention kernel 读取 **所有历史 token 的 KV**（dense attention）。

**成本**：主要是 dense attention 读长上下文（128k token）。不需要 predictor、不需要 CPU/GPU 搬运。

### 6.3 attnpredict-offload decode（重点）

#### 步骤 1：`_prepare_decode()`

[attnpredict_offload.py:1503](src/sparsevllm/engine/cache_manager/attnpredict_offload.py#L1503)：

1. 为每个序列当前新 token 分配 **CPU full backing slot**（`_allocate_cpu_slots`）；
2. 记录 `_decode_rows`（每个序列的 cache row）和 `_decode_current_positions`（当前 token 的逻辑位置）；
3. GPU `slot_mapping` 先放 -1 占位（不在此处分配 GPU slot）；
4. 设置每层 `LayerBatchStates`。

**为什么不在这里分配 GPU slot**：因为每一层的 K/V 不同，decode 新 token 在每层的 KV 需要分别写入各层 cache。代码选择在每层真正进入 `get_layer_store_view(layer)` 时再处理，这样能和该层的 prefetch 结果自然 overlap。

#### 步骤 2：每层 attention 前 —— `get_layer_store_view(layer_idx)`

[attnpredict_offload.py:867](src/sparsevllm/engine/cache_manager/attnpredict_offload.py#L867)：

这是 offload decode 的 **"按层消费点"**，也是整个 decode 路径最复杂的函数。

1. **消费 prefetch**：`_consume_prefetch(layer_idx, wait)` 检查后台预测是否完成。如果新 lease 还没好，继续用旧 lease；如果旧 lease 超过 `max_stale_steps`，才等待。

2. **组合目标 positions**：对每个序列，组合本次 attention 需要可见的 token 位置：
   ```
   sink tokens (0..63)
   + hot tokens (CNN 预测的历史重要 token)
   + recent tokens (最近 512 个 token)
   + current token (当前 decode token)
   ```

3. **Residency diff**：`_ensure_positions_resident()` 比较旧 GPU 驻留集合和新目标集合：
   - `to_free = old - target`：释放不需要的 GPU slot（dirty token 先写回 CPU）；
   - `missing = target - old`：从 CPU full backing 加载缺失 token 的 K/V 到 GPU。

4. **分配当前 token 的本层 GPU slot**：`_ensure_current_decode_slots()` 为当前 decode token 分配本层 GPU active slot。

5. **返回** `(k_cache, v_cache, slot_mapping)` 给 `Attention.forward()`。

#### 步骤 3：`build_decode_view()`

[attnpredict_offload.py:1097](src/sparsevllm/engine/cache_manager/attnpredict_offload.py#L1097)：

将逻辑 token positions 转成 packed GPU slots 供 decode attention kernel 使用。

```
sparse view positions: [0, 1, ..., 63, 2000, 5000, ..., 9489, ..., 10000]
    → 查 GPU slot mirror →
packed slots: [88, 91, ..., 155, 3001, 42, ..., 777, ..., 900]
```

输出：
- `packed_slots[batch_size, max_keep]`：每行每列是一个 GPU slot ID；
- `view_lens[batch_size]`：每行实际可见 token 数；
- `local_req_indices`：`[0, batch_size)` 局部索引。

内部还维护 `_static_view_cache`（lease 内稳定的 sink/hot slots 缓存避免重复构造）和 `_packed_slots_cache`（缓冲复用避免每层分配）。

#### 步骤 4：decode attention kernel

[attention.py:238-316](src/sparsevllm/layers/attention.py#L238)：

两阶段 flash decoding：
- **stage1**：`gqa_flash_decode_stage1` 或带分数输出的 `gqa_flash_decode_stage1_with_score`，分块计算局部 attention；
- **stage2**：`flash_decode_stage2` 合并所有块得到最终输出。

如果当前 step 需要刷新 predictor（`should_collect_decode_attn_score` 返回 True），使用 `with_score` kernel 额外写出 logits 到 `attn_score`。`decode_attn_score_max_len` 返回 packed view 的上界长度，避免分配完整上下文长度的 score buffer。

#### 步骤 5：`on_kv_stored()`

[attnpredict_offload.py:938](src/sparsevllm/engine/cache_manager/attnpredict_offload.py#L938)：

- **prefill**：立即写入 CPU full backing；
- **decode**：只标记 dirty（`(row, pos)` 加入 `_dirty_gpu_positions`），不立即 D2H。只有该 token 将要被驱逐时才补写 CPU（lazy writeback）。

#### 步骤 6：predictor / prefetch

`SparseController.on_attention_end()` → `cache_manager.predict_next_mask(layer_idx, attn_logits)`。

[attnpredict_offload.py:1210](src/sparsevllm/engine/cache_manager/attnpredict_offload.py#L1210)：

1. 记录 CUDA event（表示 attention kernel 已写完 logits）；
2. 提交后台任务到 `ThreadPoolExecutor`；
3. 后台 worker 在 prefetch stream 上：
   - 等待 event 完成；
   - 对 logits 做 softmax → block pooling → 更新 `attn_history`；
   - CNN predictor（已 `torch.compile`）预测下一步 hot tokens；
   - 生成新 lease（`_expand_layer_results` 复制给组内 4 层）；
   - 预取缺失 KV 从 CPU 到 GPU（`_ensure_positions_loaded`）；
   - 记录 done event。

**跨层复用**：`_layer_reuse_stride = 4`，每 4 层为一组，只让组首层（`layer_idx % 4 == 0`）收集 score 并跑 predictor，组内其它层复用结果。

**跨步复用**：`_reuse_steps = 16`，每 16 个 decode step 才刷新一次 predictor。`should_collect_decode_attn_score()` 控制是否收集 score。

#### 步骤 7：eviction / residency

- `_resident_positions[layer][row]`：当前 GPU active pool 中驻留的 token positions 集合；
- `gpu_req_to_token_slots_cpu[layer]`：CPU 侧 GPU residency 镜像（`mirror[row, pos] = gpu_slot`，-1 表示不在 GPU）；
- `_ensure_positions_resident()` 执行 residency diff，释放旧 token、加载新 token；
- dirty token（GPU 有新 KV 但 CPU 没有）在驱逐前先 `_copy_dirty_gpu_to_cpu()` 写回；
- `_allocate_gpu_slots_locked()` / `free_slots_stack` 维护 per-layer GPU slot 生命周期。

## 7. vanilla 与 attnpredict-offload 的关键差异

| 维度 | vanilla | attnpredict-offload |
|---|---|---|
| KV 存储位置 | 全部在 GPU | GPU active pool + CPU full backing |
| GPU 显存占用 | 约 66GB (128k/bs=2) | 约 49GB |
| CPU 内存占用 | 无 | 约数十 GB（完整 KV backing） |
| decode attention 读取范围 | 全部历史 token | sink + hot + recent + current（约 4096 token） |
| 是否有 predictor | 否 | 是（CNN，`torch.compile`） |
| 是否有 prefetch | 否 | 是（异步 CUDA stream） |
| 是否有 score buffer | 否 | 是（仅 predictor 刷新步，packed view 宽度） |
| 是否有 lease | 否 | 是（hot tokens 跨步复用，16 步刷新） |
| 是否有 GPU/CPU 数据搬运 | 否 | 是（H2D 预取 + D2H dirty 写回） |
| 主要性能瓶颈 | dense attention 读长上下文 | predictor GPU 负载 + per-layer Python 调度 + CPU backing 写入 |
| 质量风险来源 | 无 | predictor 预测不准、跨层近似、跨步 stale |

## 8. 具体例子：128k prompt / batch size=2 / output_len=64 / attnpredict-offload

### 8.1 两条序列进入

```
seq0: 128000 tokens prompt
seq1: 128000 tokens prompt
```

### 8.2 chunk prefill 推进

`chunk_prefill_size = 4096`，每个序列需要 `128000 / 4096 ≈ 31` 个 chunk。每轮 prefill 一个 chunk，调度器每次从 `waiting` 取出当前 chunk。

每个 chunk：
- 分配 CPU full backing slots（跨层共享）；
- 每层分配 GPU active slots（per-layer）；
- 完整 attention 读取已有历史 + 当前 chunk；
- `on_kv_stored()` 同步写入 CPU backing。

### 8.3 最后一个 prefill chunk

- `prepare_prefill_predictor_inputs()` 创建 `tail_score[2, 32, 64, pooled_len]`；
- `context_attention_fwd()` 做完整 attention，旁路写 block 级 tail score；
- `on_prefill_layer_end()` 提交后台 CNN 预测 + 预取首个 decode hot tokens；
- 每 4 层只让组首层（0, 4, 8, 12, 16, 20, 24, 28）跑 predictor，其余复用。

### 8.4 CPU full backing 保存完整 KV

prefill 结束后，CPU backing 保存了两条序列各 128000 个 token 的完整 K/V（每层）。GPU active pool 可能已被部分释放，只保留 predictor 选出的 hot tokens + sink + recent。

### 8.5 decode 第 1 步

1. `_prepare_decode()`：为 pos=128000 分配 CPU slot，记录 rows/positions；
2. 每层 `get_layer_store_view()`：
   - 消费 prefill 阶段提交的后台预测（首个 lease）；
   - 组合：sink(0..63) + hot(CNN 预测的 3520 token) + recent(127488..127999) + current(128000)；
   - 确保这些 token 驻留 GPU active pool（prefill 已预取大部分）；
   - 为 current token 分配本层 GPU slot；
3. `store_kvcache()` 写入 current K/V；
4. `build_decode_view()` 构造 packed slots（约 4096 个）；
5. decode attention kernel 只读这约 4096 个 token（而非 128001）；
6. `predict_next_mask()` 提交后台预测（如果需要刷新）。

### 8.6 decode 第 2-16 步复用 lease

`should_collect_decode_attn_score()` 检查：lease 使用步数 < `reuse_steps=16`，且无缺失 row，且后台无未完成 future → 返回 False，不收集 score。

这些步：
- 不用 `with_score` kernel（更快）；
- 不跑 CNN predictor；
- 只做 residency diff（recent window 滑动 1 位）+ packed view 构造。

### 8.7 第 17 步重新预测

lease 使用步数达到 16，`should_collect_decode_attn_score()` 返回 True：
- 使用 `with_score` kernel 写出 logits；
- `predict_next_mask()` 提交后台 CNN 预测 + 预取；
- 下一步到同一层时消费新 lease。

### 8.8 每 4 层跨层复用

layer_reuse_stride=4，组首层（0,4,8,...,28）跑 predictor，组内层（1,2,3,5,6,7,...）复用组首层的 hot positions 和 lease。predictor 触发层数从 32 降到 8。

### 8.9 sink=64, recent=512, top=4096 的含义

每个序列每层的可见 token：
```
sink:   positions 0..63           (64 token，序列开头固定保留)
hot:    CNN 预测的 3520 token     (4096 - 64 - 512 = 3520，中间历史区域)
recent: positions 127488..127999  (512 token，最近 token 固定保留)
current: position 128000          (当前 decode token)
```

### 8.10 packed view 大致包含

```
packed_slots[0, :] ≈ [sink GPU slots] + [hot GPU slots] + [recent GPU slots] + [current GPU slot]
packed_slots[1, :] ≈ 同上（seq1 的对应 slots）
view_lens ≈ [4096, 4096]（边界去重可能略有差异）
```

### 8.11 预测、prefetch、attention 三者如何 overlap

```
时间线（单层）：
  主 stream: attention kernel → MLP → 下一层 attention ...
  prefetch stream: [wait event] → CNN predict → H2D prefetch → [record done event]

下一次同层到达时：
  get_layer_store_view() → _consume_prefetch(wait=True) → wait done event → 消费新 lease
```

关键：前面层的计算和后面层的后台预取自然 overlap，不需要在 step 开头等待所有层。

### 8.12 为什么 DecTP 高于 vanilla 但 TTFT 仍慢

- **DecTP 更高**：decode attention 只读约 4096 token 而非 128000 token，attention 计算量大幅减少；predictor 刷新频率低（16 步一次），大部分 decode 步不跑 CNN。
- **TTFT 更慢**：prefill 每层每 chunk 都要做 CPU full backing 写入（D2H），Nsight 显示 `cudaMemcpyAsync` 占 CUDA API 时间 98.3%。

## 10. 当前性能状态和瓶颈

### 10.1 当前稳定目标 benchmark

| method | TTFT | PreTP | DecTP | ITL | Mem | Decode speedup |
|---|---:|---:|---:|---:|---:|---:|
| vanilla | 42.75s | 5988 tok/s | 46.56 tok/s | 42.96ms | 66.49GB | 1.00x |
| attnpredict-offload | 53.17s | 4815 tok/s | 51.21 tok/s | 39.06ms | 48.74GB | 1.10x |

### 10.2 主要瓶颈

1. **prefill CPU full backing 写入**：每层每 chunk 都要做 D2H copy + CPU index_copy_，是 TTFT 慢的主要原因。Nsight 显示 `cudaMemcpyAsync` 占 CUDA API 时间 98.3%。
2. **CPU/GPU D2H/H2D 数据搬运**：dirty KV 写回和 hot KV 预取。
3. **per-layer Python 调度成本**：`build_decode_view()` 每层每步约 0.16ms，32 层 × 64 步 = 约 330ms。
4. **Predictor 固定成本**：CNN forward + block pooling + top-k + lease 切换 + 预取调度。
5. **Prefetch event 等待**：某些层会等待上一轮后台预取完成。

### 10.3 已验证无效或负收益的方向

| 方向 | 结果 |
|---|---|
| fused logits → block pooled attention runtime kernel | 正确但更慢 |
| 同层 batch CNN | 低于稳定版 |
| CPU CNN predictor | 极慢（0.43 tok/s） |
| 过大 stale（>16 步） | 质量风险 |
| 降低 top-k（2048） | 小幅提速但压缩质量预算 |
| 非 offload attnpredict | 3.11 tok/s，不可替代 |
| GPU kernel 下沉 build_decode_view slot gather | 端到端负收益 |
| split static slots + recent ring decode kernel | 更慢 |
| 延迟 prefill CPU backing 写直到 eviction | DecTP 从 50 降到 5 |
| layer_reuse_stride=8/16/32 | 未超过 vanilla 或质量风险过高 |
| incremental packed view append | 更慢 |
| decode attention BLOCK_SEQ 调参 | 256 最优 |

## 11. 当前最终配置

| 参数 | 值 | 原因 |
|---|---|---|
| `attnpredict_reuse_steps` | 16 | 跨步复用，减少 predictor 刷新频率 |
| `attnpredict_max_stale_steps` | 16 | 后台预测未完成时最多复用旧 lease 16 步 |
| `layer_reuse_stride` | 4 | 跨层复用，每 4 层一组共享预测结果 |

| `num_recent_tokens` | 512 | 最近 token 固定保留 |

| 单条默认优先级 predictor/prefetch CUDA stream | - | 减少多流并发抢占主 stream |
| `torch.compile` CNN predictor | dynamic=True, triton.cudagraphs=False | 减少 predictor forward 的 Python 调度开销 |

## 12. 简短伪代码

### vanilla decode

```python
def vanilla_decode_step(seqs):
    # 1. 准备：为每个序列分配 1 个新 GPU slot
    new_slots = allocate_batch(seq_ids, size=1)
    slot_mapping = new_slots  # 所有层共享
    context_lens = row_seq_lens  # 所有层共享

    # 2. 每层 attention
    for layer_idx in range(num_layers):
        store_kvcache(k, v, kv_cache[layer_idx], slot_mapping)
        # 读取完整历史
        active_slots = buffer_req_to_token_slots  # 全局映射表
        # decode attention: 读全部历史 KV
        o = flash_decode(q, k_cache, v_cache, active_slots, context_lens)

    # 3. 采样
    token = sample(logits)
    return token
```

### attnpredict-offload decode

```python
def offload_decode_step(seqs):
    # 1. 准备：只分配 CPU backing slot，GPU slot 逐层分配
    cpu_slots = allocate_cpu_slots(seq_ids, size=1)
    _decode_rows = rows
    _decode_current_positions = positions
    slot_mapping = [-1] * batch_size  # 占位

    # 2. 每层 attention
    for layer_idx in range(num_layers):
        # 2a. 消费上一轮 prefetch（如果完成）
        consume_prefetch(layer_idx, wait=stale_timeout)

        # 2b. 组合目标 positions: sink + hot + recent + current
        target = compose_positions(hot_lease, full_len)

        # 2c. residency diff: 释放旧 token，加载缺失 token
        ensure_positions_resident(layer_idx, target)

        # 2d. 为当前 token 分配本层 GPU slot
        current_slot = allocate_gpu_slot(layer_idx)
        slot_mapping = [current_slot]

        # 2e. 写入当前 token 的 K/V
        store_kvcache(k, v, gpu_kv_cache[layer_idx], slot_mapping)
        mark_dirty(row, pos)  # 不立即写 CPU

        # 2f. 构造 packed view
        packed_slots, view_lens = build_decode_view(layer_idx)

        # 2g. decode attention（只读 packed view）
        if need_refresh(layer_idx):
            o, logits = flash_decode_with_score(q, packed_slots, view_lens)
        else:
            o = flash_decode(q, packed_slots, view_lens)

        # 2h. 异步预测下一步
        if need_refresh(layer_idx):
            submit_background(layer_idx, logits)  # CNN predict + prefetch

    # 3. 采样
    token = sample(logits)
    return token
```
