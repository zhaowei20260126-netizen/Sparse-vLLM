# AttnPredict-Offload 总技术方案

本技术方案将介绍 `attnpredict-offload` 目前的所有优化点，按类别组织。每个优化点都包含**核心原理**、**背景**、**优化方法**、**收益来源**、**质量影响**和**实验结果**。

> 总体结论：最终性能提升不是靠单一参数取得，而是跨步复用、跨层复用、predictor 固定成本优化、packed view 构造优化、CPU backing 写入优化共同叠加的结果。

## 一、主收益策略

### 优化1：跨步复用与 max stale 控制

> 核心原理：把同一份 predictor 结果连续复用多个 decode step，只在达到刷新步数后重新收集 score 和预测，从而减少 predictor、score 写出和 prefetch 调度次数。

#### 1.1 背景

`AttentionPredictor`（注意力预测器，即根据历史 attention 模式预测下一步重要 token 的模块）如果频繁刷新，会在 decode 阶段反复触发：

- attention score 写出；
- CNN predictor forward；
- block score 到 hot tokens 的转换；
- lease 切换和 KV prefetch。

这些开销虽然与主计算流存在异步 overlap，但在 Sparse-vLLM 集成后仍然会消耗 GPU、CPU 调度和 H2D（Host to Device，CPU 到 GPU 数据传输）/D2H（Device to Host，GPU 到 CPU 数据传输）资源。

#### 1.2 优化方法

当前配置采用：

```text
attnpredict_reuse_steps = 16
attnpredict_max_stale_steps = 16
```

`reuse_steps` 控制同一份 hot tokens 复用多少步；`max_stale_steps` 控制后台预测未完成时，旧结果最多继续使用多少步。

> 说明：这不是无限复用。达到 `reuse_steps` 后会尝试刷新 predictor；只有后台还没完成时，才允许继续使用旧结果到 `max_stale_steps`。

#### 1.3 为什么有收益

- predictor 刷新频率下降；
- score buffer 分配和 with-score decode kernel 调用次数下降；
- CNN forward、top-k、lease 切换和 prefetch 任务数量下降；
- 普通复用步只构造 sparse read view，不重新预测。

#### 1.4 质量影响

该优化会降低预测新鲜度，因此有质量风险。当前没有使用极大 stale 或极小 top-k；配合 `top-k=4096 / sink=64 / recent=512`，LongBench 英文小样本 A/B 未发现输出变化。

#### 1.5 实验结果

`128k / bs=2 / output_len=64` 相关结果：

| 配置 | DecTP |
|---|---:|
| 初始稳定 `reuse=4 / stale=6` | 约 24.45 tok/s |
| `reuse=8 / stale=8` | 44.65 tok/s |
| `reuse=12 / stale=12` | 47.92 tok/s |
| `reuse=16 / stale=16` | 50.50 tok/s |
| 最终同轮 benchmark | 51.21 tok/s |
| 当前同机最新结果 | 52.33 tok/s |

> 观测结果：跨步复用是 decode 吞吐超过 vanilla 的主要贡献之一，但单独增大 reuse 不足以复现最终速度，仍需要跨层复用和 runtime 固定成本优化配合。

### 优化2：跨层复用 stride=4

> 核心原理：每 4 层只让复用组首层运行 predictor，其余层复用同一组 hot tokens 和 lease，减少重复预测和预取调度。

#### 2.1 背景

原始逐层 predictor 路径会让每一层都收集 attention score 并预测 hot tokens。对 32 层模型来说，decode 刷新步会产生 32 次 predictor 相关任务。

相邻层 attention 模式并不完全相同，但在较大的 token 预算下，组内复用可以作为速度和质量之间的折中。

#### 2.2 优化方法

当前固定：

```text
layer_reuse_stride = 4
source layers = 0, 4, 8, ..., 28
```

组首层负责收集 attention score、运行 predictor、生成 hot positions，并把结果映射到组内其它层。组内其它层直接复用组首层预测出的 hot positions。

> 说明：跨层复用只减少 predictor 路径；每层自己的 K/V cache、GPU slot 和 packed view 仍然独立构造，不能跨层共享物理 slot。

#### 2.3 为什么有收益

- predictor 触发层数从 32 降到 8；
- score buffer 数量减少；
- CNN forward 和 top-k 次数减少；
- prefetch worker 任务数量减少。

#### 2.4 质量影响

这是有质量假设的优化。不同层的 attention 分布可能不同，stride 太大时风险升高。当前采用 `stride=4`，LongBench 英文小样本未发现输出变化。

#### 2.5 实验结果

当前代码消融实验：

| 实验 | DecTP | 结论 |
|---|---:|---|
| vanilla | 46.62 tok/s | full attention 基线 |
| 当前代码不启用跨步/跨层复用 `layer_reuse_stride=1 + reuse/max_stale=1/1` | 10.32 tok/s | 每层每步都预测，开销最大 |
| 当前代码不启用跨层复用 `layer_reuse_stride=1 + reuse/max_stale=16/16` | 37.03 tok/s | 每层都预测，低于 vanilla |
| 当前代码启用跨层复用 `layer_reuse_stride=4 + reuse/max_stale=16/16` | 52.33 tok/s | 超过 vanilla |

> 观测结果：在当前 runtime 优化已经存在的代码上，不做任何复用只有 `10.32 tok/s`；只加跨步复用后提升到 `37.03 tok/s`；再加跨层复用后提升到约 `52.33 tok/s`。说明跨步复用和跨层复用都是当前超过 vanilla 的关键组成。

## 二、Predictor 与异步调度优化

### 优化3：CNN predictor 的 torch.compile 和预热

> 核心原理：用 `torch.compile` 编译 CNN predictor，并在初始化时提前预热，减少正式 decode 中 predictor forward 的 Python 调度和首次编译开销。

#### 3.1 背景

CNN predictor 在刷新步中根据历史 attention score 预测 hot tokens。即使刷新频率已经降低，它仍然会在 decode 阶段消耗 GPU kernel launch 和 Python 调度时间。

`torch.compile`（PyTorch 图编译，即把 eager 执行转换成更少调度开销的编译图）可以减少 predictor forward 的固定开销。

#### 3.2 优化方法

当前代码对 `self.cnn` 做编译：

```python
self.cnn = torch.compile(
    self.cnn,
    dynamic=True,
    options={"triton.cudagraphs": False},
)
```

随后用最大宽度附近的 dummy 输入预热：

```python
self.cnn(dummy)
torch.cuda.synchronize()
```

> 说明：预热只为了让编译和相关 GPU 初始化提前发生，不改变 predictor 权重或输出。

#### 3.3 为什么有收益

- 减少 CNN predictor forward 的 Python 调度；
- 减少小 kernel launch 负担；
- 避免第一次真实 decode 刷新步才触发编译。

#### 3.4 质量影响

不改变 predictor 权重、输入语义和 token 选择逻辑，因此不影响输出质量。

#### 3.5 实验结果

该优化和跨层复用、跨步复用一起进入最终实现，没有单独保留独立 ablation 表。

| 指标 | 当前状态 |
|---|---:|
| 是否已接入当前实现 | 是 |
| 作用阶段 | decode predictor 刷新步 |
| 是否改变质量预算 | 否 |
| 独立优化前后对比 | 暂未单独测量 |

### 优化4：单条默认优先级 predictor/prefetch stream

> 核心原理：把多层后台 predictor/prefetch 任务收敛到一条默认优先级 CUDA stream，减少多 stream 并发对主计算流的抢占和调度竞争。

#### 4.1 背景

`CUDA stream`（CUDA 流，即 GPU 上异步排队执行 kernel/copy 的队列）可以让后台预测和主 attention 计算 overlap。但 stream 不是越多越好。

如果每层都有独立 stream，多个 predictor 和 H2D copy 可能同时争抢 GPU 计算资源、显存带宽或 PCIe 带宽，反而拖慢主计算流。

#### 4.2 优化方法

当前代码使用一条默认优先级 stream：

```python
self._prefetch_stream = torch.cuda.Stream(priority=0)
self._prefetch_streams = [self._prefetch_stream for _ in range(self.num_layers)]
```

所有 source layer 的后台 predictor/prefetch 都进入这条 stream 排队。

同时，当前实现已经去掉同步/异步配置开关，`attnpredict-offload` 固定使用异步 prefetch 路径：

```text
async_prefetch = always
```

> 说明：该优化保留异步 overlap，但限制后台任务并发强度，让它更像有序后台流水。固定异步后，代码不再维护同步 fallback，避免两套时序逻辑同时存在。

#### 4.3 为什么有收益

- 减少多 stream 调度开销；
- 避免后台 predictor 同时挤占主 attention kernel；
- event 等待关系更简单，降低消费 prefetch 时的时序复杂度。

#### 4.4 质量影响

只改变后台任务排队方式，不改变 predictor 输入、hot tokens 或 sparse view，因此不影响输出质量。

#### 4.5 实验结果

该优化作为最终实现的一部分采纳，没有单独保留可靠 ablation。

| 指标 | 当前状态 |
|---|---:|
| 是否已接入当前实现 | 是 |
| 作用阶段 | decode predictor/prefetch |
| 是否改变质量预算 | 否 |
| 独立优化前后对比 | 暂未单独测量 |

> 观测结果：Nsight Systems 已确认 predictor stream 和 main stream 存在 overlap；当前更可信的后续方向是评估“source layer 组级 stream”，而不是恢复每层一个 stream。

### 优化5：block pooling 和 top-k 小张量优化

> 核心原理：复用 block 展开 offsets，去掉会触发同步的小判断，并用更轻的排序替代不必要的去重，减少 predictor 后处理中的小张量开销。

#### 5.1 背景

predictor 刷新步会把 attention logits 转为 block score，再选出 hot tokens。

`block pooling`（块级池化，即把 token 级分数按固定 token block 聚合）和 top-k 后处理里有不少小 Tensor 操作。这类操作单次不大，但在 source layer 刷新步反复出现。

#### 5.2 优化方法

当前实现采用：

- 缓存 `_pooling_offsets_gpu`，避免每次创建 `torch.arange(block_size)`；
- 去掉 `valid.any()` 这类可能触发同步的小判断；
- 在 top-k block 已互异的场景，用 `.sort().values` 替代更重的 `torch.unique`。

> 说明：top-k block 本身已经互异时，再做 unique 只是额外整理，不改变结果集合。

#### 5.3 为什么有收益

- 减少小 Tensor 分配；
- 减少潜在 CPU/GPU 同步；
- 降低 predictor 后处理固定成本。

#### 5.4 质量影响

排序不改变 hot token 集合；缓存 offsets 不改变计算结果，因此不影响输出质量。

#### 5.5 实验结果

该优化作为 predictor 后处理固定成本优化的一部分接入，没有单独 ablation。

| 指标 | 当前状态 |
|---|---:|
| 是否已接入当前实现 | 是 |
| 作用阶段 | decode predictor 刷新步 |
| 是否改变 token 集合 | 否 |

## 三、Decode runtime 固定成本优化

### 优化6：decode view 长度缓存避免 `.item()` 同步

> 核心原理：在 `build_decode_view()` 的 CPU 路径中缓存本层 packed view 最大长度，attention 侧直接读取缓存值，避免每层从 GPU Tensor 上 `.item()`。

#### 6.1 背景

`.item()` 同步（GPU 标量读回 CPU，即 CPU 为拿到一个 GPU Tensor 数值而等待 GPU 完成相关任务）在 decode hot path 中很贵。

decode attention 需要知道本 batch 的最大可见 KV 长度，用来分配中间 buffer。对 `attnpredict-offload` 来说，这个长度其实在 `build_decode_view()` 里已经由 CPU 侧 `keep_counts` 算出来。

#### 6.2 优化方法

`build_decode_view()` 中记录：

```python
self._decode_view_max_lens[layer_idx] = max_keep
```

attention 侧通过 cache-manager hook 读取：

```python
cache_manager.decode_view_max_len(layer_idx, layer_context_lens)
```

> 说明：这里返回的是 packed sparse view 的最大有效长度，不是原始完整上下文长度。

#### 6.3 为什么有收益

- 避免每层 decode 从 GPU 上取 `context_lens.max().item()`；
- 减少 CPU/GPU 同步点；
- 长度来自同一次 packed view 构造，不需要重复计算。

#### 6.4 质量影响

只改变长度获取方式，不改变可见 token 集合和 attention 计算，因此不影响输出质量。

#### 6.5 实验结果

该优化已接入当前实现，但没有单独拆分实验。

| 指标 | 当前状态 |
|---|---:|
| 是否已接入当前实现 | 是 |
| 作用阶段 | decode 每层 attention 前 |
| 是否直接改变 token 选择 | 否 |
| 独立优化前后对比 | 暂未单独测量 |

### 优化7：build_decode_view 的 packed view 固定成本优化

> 核心原理：把 lease 内稳定的 sink/hot slots 缓存下来，recent 部分用连续切片动态补齐，并复用 packed slots/local req indices buffer，减少每层每步 view 构造成本。

#### 7.1 背景

`packed view`（打包读视图，即把每条请求本层实际要读的 GPU slot 压成二维表）是 decode attention kernel 的输入。

`attnpredict-offload` 每层每步都要把：

```text
sink + hot + recent/current
```

转换成：

```text
packed_slots[batch, visible_len]
view_lens[batch]
```

这条路径频率高，即使单层耗时不大，32 层累计后也会成为固定开销。

#### 7.2 优化方法

当前实现包含几项组合优化：

- `_static_view_cache` 缓存 lease 内稳定的 sink/hot slots；
- recent slots 使用连续切片：

```python
mirror[row_idx, recent_start:full_len]
```

- `_packed_slots_cache` 复用 packed slots buffer；
- `_local_req_indices_cache` 复用局部 batch 索引；
- source layer 的 `_packed_positions_cache` 复用 positions buffer。

> 说明：static 部分在同一 lease 内不变；recent/current 每步随序列长度滑动，所以只能动态补。

#### 7.3 为什么有收益

- 避免每步重复构造 sink/hot 的 GPU slot Tensor；
- recent 连续切片替代 `np.arange + advanced indexing`；
- 减少小 GPU Tensor 分配；
- 减少每层每步 Python/cache-manager 固定成本。

#### 7.4 质量影响

该优化不改变 `sink + hot + recent/current` 集合，只改变 view 构造方式，因此不影响输出质量。

#### 7.5 实验结果

实验配置为 `128k / bs=2 / output_len=16`：

| 指标 | 优化前 | 优化后 |
|---|---:|---:|
| build_decode_view 平均耗时 | 0.1729 ms/layer | 0.1614 ms/layer |
| DecTP | 50.49 tok/s | 52.53 tok/s |

> 观测结果：该优化直接减少 decode 每层 view 构造成本，端到端有小幅正收益。

### 优化8：decode view 保存 CPU metadata

> 核心原理：在构造 packed view 时同步保存 CPU 侧 metadata，predictor 后处理直接读 CPU 数据，避免后续从 GPU Tensor 逐项取标量。

#### 8.1 背景

预测下一轮 hot tokens 时，需要知道 sparse logits 对应的 batch row、view length、full context length 和 packed position。

如果后处理阶段再从 GPU Tensor 上取这些标量，容易触发 `.item()` 或 D2H 小同步。

#### 8.2 优化方法

`build_decode_view()` 在 source layer 预测步保存：

```python
self._last_decode_view[layer_idx] = {
    "positions": packed_positions.detach(),
    "req_indices_cpu": rows_cpu,
    "view_lens_cpu": keep_counts,
    "full_context_lens_cpu": full_lens,
}
```

> 说明：CPU metadata 和 packed view 来自同一次构造，语义一致；这里只避免后处理阶段重复从 GPU 读标量。

#### 8.3 为什么有收益

- predictor 后处理不再逐项读取 GPU 标量；
- 减少 CPU/GPU 同步点；
- 让后台 worker 更少依赖主计算流状态。

#### 8.4 质量影响

metadata 与 GPU view 同源，不改变 logits、hot tokens 或 attention 可见集合，因此不影响输出质量。

#### 8.5 实验结果

该优化已接入当前实现，没有单独拆分 ablation。

|---|---:|
| 是否已接入当前实现 | 是 |
| 作用阶段 | decode predictor 后处理 |
| 是否改变质量预算 | 否 |
| 独立优化前后对比 | 暂未单独测量 |

### 优化9：packed positions 仅在预测步构造

> 核心原理：普通复用步只构造 attention 必需的 packed slots，只有本层本步真正收集 score 时才构造 packed positions 和 predictor metadata。

#### 9.1 背景

`packed_positions`（打包逻辑位置表，即 `packed_slots` 中每个 GPU slot 对应的原始 token position）只用于把 sparse attention logits 还原到完整逻辑位置，供 predictor 更新 hot tokens。

普通复用步不会收集 attention score，也不会调用 predictor。如果 source layer 每步都构造 `packed_positions`，就会产生无用的 Tensor 构造、copy 和 metadata 保存。

#### 9.2 优化方法

当前新增 `_collect_decode_positions[layer_idx]` 记录本轮 decode 是否真正需要 positions metadata。

`should_collect_decode_attn_score()` 在 controller 决定是否分配 score buffer 时同步记录：

```python
self._collect_decode_positions[layer_idx] = collect
```

`build_decode_view()` 只在预测步构造：

```python
need_positions = self._collect_decode_positions[layer_idx]
```

> 说明：不能在 `build_decode_view()` 里重新调用判断函数，因为 `get_layer_store_view()` 可能已经消费 future，状态会变化；这里必须复用 controller 当时做出的本轮决策。

#### 9.3 为什么有收益

- 普通复用步 source layer 不再构造 `packed_positions`；
- 不再为 static positions 创建 GPU Tensor；
- 不再为 recent positions 创建 `torch.arange`；
- 不再保存无用 `_last_decode_view`。

#### 9.4 质量影响

该优化不改变 attention 读取的 `packed_slots`，也不改变 predictor 触发条件；只是跳过复用步无用 metadata，因此不影响输出质量。

#### 9.5 实验结果

该优化是 2026-06-06 新增的小型 runtime 瘦身，目前只完成语法检查，未单独跑 benchmark。

| 指标 | 当前状态 |
|---|---:|
| 是否已接入当前实现 | 是 |
| 作用阶段 | decode source layer 普通复用步 |
| 是否改变 token 集合 | 否 |
| 独立优化前后对比 | 暂未单独测量 |

## 四、Prefill 与 CPU backing 优化

### 优化10：CPU backing 连续段写入优化

> 核心原理：当 prefill 分配到的 CPU slots 是连续递增区间时，用连续切片 `copy_` 替代 `index_copy_` 索引写入，减少 CPU backing 落入阶段的索引处理开销。

#### 10.1 背景

在 `attnpredict-offload` 中，完整历史 KV 不全部常驻 GPU，而是保存在 CPU backing 中。prefill 阶段每一层生成新的 K/V 后，都需要把这批 K/V 从 GPU 写入 CPU backing，保证后续如果 GPU active pool 中的 KV 被驱逐，仍然可以从 CPU 恢复。

原实现统一使用 `index_copy_` 按 `cpu_slots` 写入：

```python
cpu_kv_cache[0, layer_idx].index_copy_(0, cpu_slots, host_k)
cpu_kv_cache[1, layer_idx].index_copy_(0, cpu_slots, host_v)
```

这种方式适合 CPU slot 不连续的情况，但如果当前 chunk 的 `cpu_slots` 实际是连续递增的，仍然要额外处理索引数组。

> 说明：即使 `cpu_slots = [5000, 5001, ...]`，`index_copy_` 也会按“读取索引 -> 定位目标 slot -> 写入”的散写流程执行，不能直接退化成简单的连续 slice copy。

#### 10.2 优化方法

在 `_prepare_prefill()` 中检测当前 chunk 分配到的 CPU slots 是否连续：

```text
cpu_slots = [5000, 5001, 5002, ..., 5999]
```

如果连续，就记录为一个连续写入片段：

```python
(token_start, token_end, slot_start, slot_end)
```

随后在 `on_kv_stored()` 中改用连续切片写入：

```python
cpu_kv_cache[0, layer_idx, slot_start:slot_end].copy_(host_k[token_start:token_end])
cpu_kv_cache[1, layer_idx, slot_start:slot_end].copy_(host_v[token_start:token_end])
```

> 适用范围：该优化只作用于 prefill 阶段的 CPU backing 写入。decode 阶段新 token 的 KV 先标记为 dirty，后续驱逐前写回 CPU 时仍走普通写回路径。

> 触发条件：当前 prefill batch 中每个 seq 的 `cpu_slots` 都必须是连续递增片段；如果某个 seq 的 slots 不连续，或者 CPU slot 分配已经碎片化，就回退到 `index_copy_`。

#### 10.3 为什么有收益

- 避免每层重复构造和消费 `cpu_slots` 索引 Tensor；
- 减少 `index_copy_` 的索引调度和散写处理；
- `_cpu_store_segments` 只在 prefill 准备阶段生成一次，后续所有 layer 都可以复用。

> 例子：一次 prefill 准备阶段得到 segment `(0, 4096, 5000, 9096)`，第 0 层到第 31 层写 CPU backing 时都可以复用这个 segment，只是写入的 `layer_idx` 不同。

#### 10.4 质量影响

该优化只改变 CPU backing 的写入方式，不改变保留 token 集合，也不改变 AttentionPredictor 的预测结果，因此不影响输出质量。

#### 10.5 实验结果

实验配置为 `128k / bs=2 / output_len=16`，只测试 `attnpredict-offload`。该优化发生在 prefill 阶段，不直接减少每个 decode step 的计算时间。

CPU backing 写入路径在一次完整推理中共调用 `1056` 次：

| 指标 | 优化前 | 优化后 |
|---|---:|---:|
| CPU backing 写入平均耗时 | 47.67 ms/次 | 47.05 ms/次 |
| 单次调用平均减少 | - | 0.62 ms/次 |
| TTFT | 53.20 s | 52.56 s |
| PreTP | 4812.18 tok/s | 4870.42 tok/s |

> 观测结果：TTFT 从 `53.20 s` 降到 `52.56 s`，说明该优化对 128k / bs=2 的 prefill 阶段有小幅正收益。

### 优化11：Prefill tail score 的 kernel 内 block pooling 写出

> 核心原理：prefill attention kernel 在正常计算 attention 输出的同时，只把最后 `history_step` 个 query 的 attention probability 按 block 做 max pooling 后写入 `tail_score`，避免先写 token 级 score 再额外做 pooling。

#### 11.1 背景

`attnpredict-offload` 需要在 prefill 最后一个 chunk 初始化 predictor history。原始语义需要拿到最后 `history_step` 个 query 对历史 KV 的注意力分数，然后按 `pooling_block_size` 压成 block 级输入。

如果先保存 token 级 attention score，再在 PyTorch 里做 pooling，路径会变成：

```text
prefill attention -> 写 token 级 score -> 额外 pooling -> 更新 predictor history
```

这会带来两个问题：

- token 级 score buffer 很大；
- prefill attention 后还要额外启动 pooling 相关张量操作。

#### 11.2 优化方法

在 `prepare_prefill_predictor_inputs()` 中创建 4D `tail_score`：

```python
(batch_size, num_heads, history_step, pooled_len)
```

其中：

```text
pooled_len = ceil(max_context_len / pooling_block_size)
```

随后 `context_attention_fwd()` 根据 4D `attn_score` 走 tail-score 分支。该 kernel 在 attention 内部完成：

```text
1. 计算正常 prefill attention 输出；
2. 只针对最后 history_step 个 query；
3. 对 KV 维度按 block 做 max pooling；
4. 直接写入 block 级 tail_score。
```

> 说明：这里融合的是“score 写出 + block pooling”，不是把 CNN predictor、top-k、lease 更新或 prefetch 全部融合进 prefill attention kernel。

#### 11.3 为什么有收益

- score buffer 从 token 级长度变成 block 级长度；
- 只收集最后 `history_step` 个 query，不保存整个 prefill chunk 的全部 query 分数；
- pooling 在 attention kernel 内完成，避免 prefill attention 后再额外做一次 token score 到 block score 的转换；
- 不改变 prefill attention 的可见 KV，也不改变模型输出 attention 结果。

> 例子：`128k` 上下文、`pooling_block_size = 16` 时，KV 维度从 `128000` 个 token 压到约 `8000` 个 block。

#### 11.4 适用范围

该优化只作用于 prefill 最后一个 chunk 的 predictor 初始化。非 source layer 会因为跨层复用跳过 predictor 初始化，因此不会创建这份 `tail_score`。

#### 11.5 实验结果

该优化已经在当前 `attnpredict-offload` prefill predictor 初始化路径中采用，但目前没有单独关闭该分支做独立 ablation。

| 指标 | 当前状态 |
|---|---:|
| 是否已接入当前实现 | 是 |
| 作用阶段 | prefill 最后一个 chunk |
| 是否直接减少单步 decode 时间 | 否 |
| 独立优化前后对比 | 暂未单独测量 |

> 观测结果：当前无法单独给出该优化点的 TTFT 或吞吐收益；可以确定的是，它减少了 prefill predictor 初始化所需的 score buffer 尺寸，并把 token score 到 block score 的转换下沉到了 attention kernel 内。

## 五、KV 生命周期与正确性优化

### 优化12：dirty KV 延迟写回与 residency 切换

> 核心原理：decode 新生成 KV 先只标记 dirty 并留在 GPU，只有它即将被驱逐时才写回 CPU backing，同时只在 lease 切换时做 residency diff。

#### 12.1 背景

`dirty KV`（脏 KV，即 GPU 中已有但 CPU backing 还没有同步保存的新 token KV）主要来自 decode 阶段。每个 decode step 都立刻 D2H 写回 CPU 会产生频繁小拷贝。

同时，普通复用步的 hot tokens 不变，如果每层每步都扫描和更新完整 residency，会产生大量 Python/cache-manager 固定成本。

#### 12.2 优化方法

当前路径：

- decode 写完 KV 后只把 `(row, pos)` 加入 `_dirty_gpu_positions[layer]`；
- 只有 `_ensure_positions_resident()` 发现该 token 要被驱逐时，才调用 dirty 写回；
- 后台预取新 lease 时使用 `release_old=False`，只加载新 token，不提前释放旧 resident；
- 主流消费新 lease 后，各层到达自身写入点时再做旧 resident 清理。

具体实现中，decode worker 返回 `needs_cleanup=True` 后，主流消费新 lease 时会把组内层标记到 `_pending_residency_cleanup`。之后每层到达 `get_layer_store_view()` 时，才按本层新 lease 做 residency diff 和旧 resident 清理。

> 说明：后台不能提前释放旧 resident，因为主计算流可能还在用旧 lease 做 attention。延后到各层自身写入点清理，可以避免后台任务和主流 attention 读同一层 KV 时发生生命周期冲突。

#### 12.3 为什么有收益

- 避免每个 decode step 都进行 D2H 写回；
- 普通复用步不做完整 residency diff；
- lease 切换时才集中处理旧 token 释放和缺失 token 加载。

#### 12.4 质量影响

该优化只改变 KV 写回和 GPU 驻留生命周期，不改变 attention 可见 token 集合；只要 dirty 驱逐前写回正确，就不影响输出质量。

#### 12.5 实验结果

该机制是当前 offload 生命周期的一部分，未单独拆分 ablation。反向实验“prefill KV 完全延迟写回到 eviction”已验证为负收益。

| 实验 | 结果 |
|---|---:|
| prefill KV 完全延迟写回 | DecTP 降到 5.08 tok/s |
| 当前 decode dirty 延迟写回 | 已采纳 |

> 观测结果：decode dirty 延迟写回合理；但把 prefill CPU backing 也延迟到驱逐会把 D2H 写回集中到 decode 临界路径，已回退。

### 优化13：`_commit_lease()` 按 row 合并

> 核心原理：提交新 lease 时只更新本次完成预测的 row，不替换整层 lease dict，避免连续 batching 下误删仍在 decode 的旧 row。

#### 13.1 背景

连续 batching 中，不同请求可能处在不同阶段：有的 row 正在 decode，有的 row 刚完成 prefill 初始化。

如果新 row 提交 lease 时直接替换整层 `_lease_hot_positions[layer]`，就会把其它仍在 decode 的 row 的 lease 删除，后续可能触发缺 row 或 KeyError。

#### 13.2 优化方法

当前 `_commit_lease()` 采用按 row 更新：

```python
lease.update(hot_positions)
self._lease_start_positions[layer_idx].update(lease_start_positions)
```

同时只清理被本次提交影响的 row 的 static cache。

> 说明：这更像正确性修复，但它也避免了连续 batching 中因 lease 生命周期错误导致的额外等待或崩溃。

#### 13.3 为什么有收益

- 保证混合 prefill/decode 下每个 row 的 lease 独立存在；
- 避免新请求初始化 lease 时破坏旧请求；
- 减少异常路径和重复初始化。

#### 13.4 质量影响

这是生命周期正确性修复，不改变固定 batch 下的预测策略，也不改变 token 选择算法。

#### 13.5 实验结果

该修复来自 LongBench 连续 batching 过程中的问题定位，没有单独吞吐 ablation。

| 指标 | 当前状态 |
|---|---:|
| 是否已接入当前实现 | 是 |
| 作用阶段 | prefill/decode 混合提交 lease |
| 主要收益 | 正确性和稳定性 |
| 独立吞吐对比 | 暂未单独测量 |

|---|---:|---:|---:|---:|---:|---:|

> 说明：显存数字不适合作为严格公平优势，因为 vanilla 和其它方法会按 GPU memory utilization 预分配更多 KV 空间；attnpredict-offload 的显存结果主要反映 active pool + CPU backing 的实现方式。

### 当前最可信瓶颈

Nsight Systems 与 profiler 结果显示，剩余主要瓶颈仍集中在：

- prefill 阶段 GPU 到 CPU 的 KV backing 写入；
- decode 每层 packed view 构造和 cache-manager 调度；
- predictor/prefetch 与主计算流 overlap 不完全；
- lease 切换时的 residency cleanup 和 event 等待。

后续更值得做的是继续减少固定成本和补完整质量评估，而不是盲目融合更多 kernel。
